# M1.5-07 — One rendering path (retire the legacy listener)

**Milestone:** M1.5 · **Size:** M · **Depends on:** — · **Status:** ✅ Done
**Written against:** commit `e9f5b8c` (2026-10-10)

## Summary

The event stream is the project's best architectural decision, but the human console is only half
migrated onto it. `TinyCI.Events.Sink.Console` renders `stage_started` / `stage_skipped`. Everything
else is rendered outside the sinks, along four paths:

- **The legacy listener.** Buffered step output, matrix rows, and retry notices go through
  `TinyCI.Listener.Human` → `TinyCI.Reporter`. The sink's own moduledoc calls this a "deferred deep
  reroute" (task T1).
- **Streaming shell output.** `TinyCI.Output` prints each line itself (`output.ex:230,235`,
  `IO.puts`, with the `[prefix]`), so in streaming mode no sink sees the console bytes.
- **Module-step output.** `TinyCI.Executor.run_step/5` writes captured module output directly with
  `IO.write` in streaming mode.
- **Hooks.** `TinyCI.Hooks` runs `on_success`/`on_failure` with no events at all.
  `TinyCI.Events.HookStarted` and `HookCompleted` are defined (`events.ex:514,540`) but nothing
  emits them.

`docs/reliability.md:39-42` lists the resulting holes ("output events arrive after step completion,
retry logs are not complete, ordinary step events lack matrix identity, and hooks are outside the
executor event stream").

For a **hosted** product this is not cosmetic: anything rendered outside the event stream is
invisible to run history and to a future web UI. The console and the UI would show different things,
which violates principle 3 ("any view of a run is a fold over it", `ROADMAP.md:61-63`) and invariant
**I2**.

## Why now

- It is foundational for the hosted UI (M3) and for the "replay/history" story; doing it before the
  server means the server inherits a correct stream rather than a half-migrated one.
- It removes a whole parallel rendering code path before more features accrete on it.

## In scope

1. Move every remaining human-facing *progress* rendering into `TinyCI.Events.Sink.Console`, driven
   purely by events: buffered step output, streaming shell lines and their `[prefix]` (today printed
   by `TinyCI.Output`), module-step output (today `IO.write` in `Executor.run_step/5`), matrix row
   headers/results, and retry notifications (`StepRetrying`). After this, `TinyCI.Output` collects
   and emits lines but prints nothing.
2. Complete the event vocabulary where events are missing to render faithfully:
   - ensure matrix identity is on ordinary step events (not just matrix run events);
   - ensure output is carried by events in the order it was produced (see the "output events arrive
     after completion" note);
   - emit `HookStarted` / `HookCompleted` from `TinyCI.Hooks`, so hooks are part of the run's
     stream (the structs exist; nothing emits them yet).
3. Retire `TinyCI.Listener.Human` and the `TinyCI.Listener` behaviour. Replace the `listener:`
   option with a `sink:`/mode selection that keeps `TinyCI.Listener.Silent`'s role (suppress
   console) without the behaviour indirection. Move the per-stage progress rendering that
   `TinyCI.Reporter` does for the listener into the sink.
4. **Keep the end-of-run summary.** `Reporter.print_summary/1` and `Reporter.format_duration/1` are
   not listener plumbing: `TinyCI.CLI.Run` prints the summary with them (`cli/run.ex:668,674`), and
   `tiny_ci runs show` renders a *past* run with them (`cli/runs.ex:182,322`, via
   `Projection.to_stage_results/1`). That is already a fold over results; keep it, whether as a
   slimmed `TinyCI.Reporter` or renamed (e.g. `TinyCI.Summary`).
5. Keep the event/JSON/NDJSON modes and secret redaction exactly as they are — the dispatcher already
   redacts at the boundary; the console sink must not re-redact or bypass it.
6. Update the byte-for-byte guards so they still assert the *same* output:
   `test/tiny_ci/events/sink/console_test.exs`, `test/tiny_ci/reporter_test.exs`.

## Out of scope

- Changing the human output format. This is a reroute, not a redesign; the guards prove it.
- The web UI (M3) — this only makes the stream complete enough for it.
- Event schema *version* bump unless an additive field is unavoidable (then follow `docs/events.md`).
- The `--events` NDJSON format beyond additive fields.

## Design notes

- The sink needs a notion of run-level ordering that the current per-event rendering lacks; the
  dispatcher already assigns a monotonic `seq` per run — render off that, and have the sink hold the
  minimal state (current stage, buffered output per step) it needs. Keep the sink a pure fold of the
  event stream.
- Streaming vs buffered is an output *mode*, not a different renderer: the sink owns both.
- `TinyCI.Listener.Silent` collapses to "attach no console sink" (already how `console_specs/2`
  works in the executor) — delete the behaviour and the two modules if nothing else uses them.
- Redaction stays at the dispatcher (`Events.Dispatcher` `redact:`); do not add a second redaction
  point in the sink.

## Pitfalls

- The current buffered mode prints a stage's step output after the stage completes; preserving that
  *timing* while sourcing it from events is the subtle part — the sink must buffer on
  `step_output` events and flush on `stage_completed`, matching today.
- Matrix rows currently print from the executor loop; matrix identity must reach the events first, or
  rendering cannot be faithful.
- Retry notices are emitted around `StepRetrying`; ensure the event carries enough (attempt, delay) to
  render the current message.

## Deviations

- The `listener:` option is replaced by `console: true | false`; `Executor.execute/4`'s fourth
  argument is now a sink-opts keyword list rather than a listener module.
- `HookStarted`/`HookCompleted` carry the hook's **name** (e.g. `:notify`) in `hook`, not the hook
  event (`on_success`). The `docs/events.md` example was corrected accordingly; per-hook granularity
  is what the console (`Hook: <name>`) and the duration/status need.
- Two additive schema-4 fields were unavoidable to render faithfully: `StepStarted.prefix` (the
  `[prefix]` the old `Output` printed for streaming parallel steps) and `StepRetrying.total` (the
  message is `[attempt n/total]`; the task's pitfall list said "delay" but the code uses `total`).
- `TinyCI.Output` now calls `:on_line` in both modes and prints nothing. Removing the prefix was
  necessary because a backend must not render (D4); the console sink owns the prefix.
- Renders via events: output lines are emitted in production order, so a retried step's earlier
  attempts' lines are now in the stream (this is what closes "retry logs are not complete").
- `StepStarted` also carries `attempts` (total planned attempts, only when >1) and `index`
  (declaration position); `MatrixRunStarted` carries `index`. These let the console reproduce the
  old `[attempt 1/N]` first-attempt notice and render buffered steps/combinations in declaration
  order rather than the racy order concurrent tasks emit in.
- **Hook timing** (minor): because hooks now run inside `run_pipeline/3`, their stderr output
  (`Hook: <name>`, failure messages) precedes the CLI's summary and "Pipeline completed" line, where
  it used to follow them. `--output json` now runs hooks before printing the JSON. stdout content is
  unchanged; only the interleaving of stderr with stdout moved.
- **DAG buffered timing** (minor, known): buffered stage output now flushes on each `StageCompleted`
  rather than once per DAG level. For multi-stage levels this interleaves with other stages'
  headers where the old code printed all level output together. The task's own design notes
  prescribe flushing on `stage_completed`, so this is intended.
- **Standalone `execute/4`** now prints buffered step output (via the ephemeral console sink). The
  old `execute/4` never called `stage_finished`, so it silently omitted it; the new behaviour is
  consistent with `run_pipeline/3`.
- **Module-step streaming output**: emitted as line events and so stamped with a `[prefix]` in a
  parallel streaming stage and with blank lines dropped, where the old `IO.write` had neither. This
  is more consistent with shell steps; the change is not guarded by a byte test.
- **Synthetic step output** ("Working directory not found", the timeout-replacement text, and an
  `unsafe_path` artifact message appended after execution) reaches `step_finished.output` but not a
  `step_output` line event. The console and `Runs.Projection` both prefer `step_finished.output`, so
  a run is still reconstructable; only a consumer that follows `step_output` alone would miss them.
- **Multi-line secrets** cannot be emitted live as `step_output` lines (a per-line redaction cannot
  match a secret spanning a line break). When any secret value contains `"\n"`, the executor skips
  live emission and emits the lines from the whole masked output instead, so nothing leaks; the
  only cost is that such a step's lines arrive when it finishes rather than as produced, and (in
  streaming mode) blank lines are dropped by `emit_step_output/3`.
- **First-attempt notice edge cases** (`[attempt 1/N]`): it is printed from `step_started`, so a
  step that is actually a cache hit (or is skipped/aborted at a `before:` breakpoint) prints it
  where the old listener did not, and a control `:retry` does not print it again. These require a
  step with both `cache:`/`retry:` or armed control, and are not in the byte guards.
- **Control `:retry` at the stage boundary** re-runs a stage without clearing the console sink's
  per-stage buffer, so a step that ran on the first pass but not the second could be printed once
  too many in buffered mode. Rare (armed breakpoints only), and not in the byte guards.
