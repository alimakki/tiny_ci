It could compete—but not by copying GitHub Actions or CircleCI feature-for-feature. The interesting angle is to lean hard into what the Erlang VM actually does unusually well.

Here’s where an Elixir/BEAM-native CI system could genuinely differentiate:

1. Massive concurrency as a first-class primitive

BEAM excels at running millions of lightweight processes with strong isolation.

What that enables:

Treat every step in a pipeline as an independent process—not just a container job
Fine-grained parallelism: split test suites dynamically at runtime based on load
Real-time scheduling (instead of static pipeline DAGs)

Differentiator:
Instead of:

“Here’s your pipeline graph, hope you sized your parallelism right”

“The system continuously rebalances work across the cluster while your pipeline runs”

2. Fault tolerance as a built-in feature (not bolted on)

BEAM’s supervision trees are basically designed for CI workloads.

Use case:

A flaky test crashes → restart just that process
A worker node dies → processes rescheduled automatically
Long pipelines survive partial infrastructure failures

Differentiator:

“Self-healing pipelines” instead of “rerun the whole job”
Step-level retries with zero orchestration overhead
3. Stateful pipelines (this is the big one)

Most CI systems are stateless between steps unless you explicitly cache or persist artifacts.

With BEAM:

You can maintain live state across the entire pipeline
Use in-memory state + message passing instead of constantly hitting storage

New possibilities:

Adaptive pipelines (change behavior mid-run)
Feedback loops (e.g., dynamically skip tests based on earlier results)
Long-lived workflows that behave more like services than scripts

This is a fundamentally different model from YAML-driven CI.

Example 2: Stateful pipeline
pipeline do
  state %{failures: 0}

  step :run_tests do |ctx|
    result = run_tests()

    if result.failed do
      ctx.failures = ctx.failures + 1
    end

    ctx
  end

  step :decision do |ctx|
    if ctx.failures > 5 do
      skip :deploy
    else
      continue()
    end
  end
end
Example 3: Dynamic scheduling
step :adaptive_tests do
  pool size: 10

  schedule fn scheduler ->
    tests = discover_tests()

    Enum.each(tests, fn test ->
      scheduler.enqueue(test)
    end)

    scheduler.on_result(fn test, result ->
      if slow?(test) do
        scheduler.increase_parallelism()
      end
    end)
  end
end

1. Execution model (the heart of the system)

Think of a pipeline as a living process tree, not a DAG.

Core idea
A pipeline = a supervised process
Each step = a child process
Each test/task = potentially its own process
State = in-memory, evolving over time

This directly leverages the Erlang VM model:

lightweight processes
message passing
supervision trees
Process hierarchy (simplified)
PipelineSupervisor
  ├── PipelineProcess (stateful)
  │     ├── StepSupervisor
  │     │     ├── StepProcess (checkout)
  │     │     ├── StepProcess (tests)
  │     │     │     ├── TestWorker 1
  │     │     │     ├── TestWorker 2
  │     │     │     └── ...
  │     │     └── StepProcess (deploy)
  │     └── StateManager
Key properties
1. Everything is restartable
A failed test ≠ failed pipeline
A crashed node ≠ lost execution
2. Everything communicates
Steps send messages to each other
Scheduler adjusts behavior mid-run
3. State lives inside the system
No constant artifact passing
No reconstructing context

defmodule Scheduler do
  def handle_result(test, result, state) do
    cond do
      slow?(test) ->
        increase_parallelism(state)

      flaky?(test) ->
        quarantine(test, state)

      true ->
        state
    end
  end
end
