# M1.5-03 — Reproducible environments for local and hosted

**Milestone:** M1.5 · **Size:** M · **Depends on:** M1.5-01, M1.5-02 · **Status:** ✅ Done (2026-10-28)
**Written against:** commit `e9f5b8c` (2026-10-10) · **Landed against:** `867f927`

## Summary

The second reason a team adopts GitHub Actions over a hand-rolled runner is reproducibility: the job
gets a *pinned* toolchain, the same one every time, on every machine. tiny_ci previously had no
answer to "which Go version does this job get?" — the answer was "whatever is installed on the host,"
which is runner drift by construction.

An environment is now explicit: an optional **`image:`** (an OCI reference) or a named host
**`environment:`** (resolved through `mise`), at pipeline or stage level. A trusted run with an image
executes shell steps in that image locally too, so a pipeline developed on a laptop and one run on
the server share the toolchain. Combined with M1.5-02, this closes the local/hosted reproducibility
gap. Cache identity includes the resolved identity, so changing the toolchain cannot reuse a stale
build.

## Why now

- It is the other half of "the pipeline you run on your laptop is the same one the server runs"
  (`ROADMAP.md:14-15`); M1.5-01/02 gave the same *code path*, this gives the same *environment*.
- Cache identity (`TinyCI.Cache`) must include the image **before** it is relied on: otherwise a
  cached build from `elixir:1.18` would be reused for `elixir:1.19`.
- Hosted runners (M4) become "a machine that can run containers," not "a machine with every
  toolchain pre-installed."

## In scope (landed)

1. `image` and `environment` as top-level directives and stage options, in `TinyCI.DSL.Spec`,
   `TinyCI.DSL.Validator`, `TinyCI.DSL.Interpreter`, the README, and the LSP (the Spec drives it).
2. A new `TinyCI.Environment` (plan/resolve/strict/cache identity), `TinyCI.Environment.Image`
   (ref validation, inspect → ID, pull-on-miss, `@sha256`), and `TinyCI.Environment.Mise` (named
   host toolchains).
3. Executor/backend wiring: the resolved image/backend is per stage, the run is planned before any
   stage starts, and every session of a stage uses one image ID.
4. Cache identity includes the image digest (or ref), toolchain name, and toolchain fingerprint for
   shell steps.
5. `--dry-run` prints the resolved environment per stage and never pulls or requires a runtime.

## Out of scope

- Building images. tiny_ci consumes images; it does not build them.
- A full Nix/Devbox integration.
- Registry auth for private images, image allow-listing, and an environment lockfile (follow-ups).
- Changing module-action execution. Module steps in an imaged stage still run in the runner's VM.
- Running `mise` in an untrusted run (`environment:` is mapped to an image or refused).

## Settled design

### DSL and spec

- Top-level directives `image "oci-ref"` and `environment "name"` / `environment :name`.
- Stage options `image:` and `environment:`.
- Validation: `image` is a non-empty binary without whitespace/control characters and must not start
  with `-` (so it can never become a runtime flag); `environment` is an atom or string matching
  `^[a-z][a-z0-9._-]{0,63}$`.
- At most one top-level `image` and one top-level `environment`; `image` and `environment` are
  mutually exclusive at the same scope. Both are rejected on steps/hooks by the existing
  unknown-option path.
- The interpreter normalizes environment atoms to strings and leaves image refs as written. Defaults
  are `nil`.

### Precedence and policy defaults

Effective declaration for a stage (first wins):

1. stage `image:`
2. stage `environment:`
3. pipeline `image`
4. pipeline `environment`
5. nothing

A stage declaration is a **whole replacement**, not a merge: `environment:` under a pipeline `image:`
runs on the host toolchain, and `--dry-run` shows it.

When nothing is declared:

- trusted → Local/host, even if the operator configured `default_image`;
- untrusted → operator `default_image`, else `{:error, :no_default_image}`;
- untrusted with `environment:` → map through `config :tiny_ci, :environments`, else
  `{:environment_requires_image, name}` (never `default_image`, never `mise`);
- an untrusted run whose stages all resolve to images, and whose shell hooks (if any) are covered,
  needs no `default_image`.

Hooks use the pipeline declaration only. Shell hooks with no pipeline declaration use the same
trust-based default; module hooks need no session. Module steps stay in the VM.

### Image resolution

`TinyCI.Environment.Image` validates the ref, asks
`TinyCI.Execution.Backend.Container.runtime/0` for the runtime, and runs
`image inspect --format '{{.Id}}' <ref>`. A missing image is pulled once when `pull: true`; with
`pull: false` (dry-run) it resolves with `digest: nil` and never pulls. A `@sha256:` ref uses the
declared digest as identity and still inspects for the local ID. Containers run by the resolved
image ID (`run_ref`), so the image cannot change between key computation and execution. Ref
validation is repeated in `Container.open/1`; an ID missing at open time fails with
`{:image_missing, id}` instead of trying to `pull` an ID.

`TinyCI.Environment.plan/3` plans only runnable stages (`TinyCI.Stage.skipped?/2`) and collects
errors without short-circuiting; `strict/1` returns the first tagged error (`{:hooks, reason}` or
`{:stage, name, reason}`). Resolution is memoized by `{image, environment}` so a ref is inspected and
a toolchain resolved once per run.

### `environment:` via mise

- `environment "default"`: `.mise.toml`, `mise.toml`, or `.tool-versions`, with `MISE_ENV` explicitly
  cleared (`""`); no config → `:no_toolchain_config`.
- Any other name requires `mise.<name>.toml` or `.mise.<name>.toml`; otherwise
  `{:unknown_environment, name, searched}` (a typo would otherwise silently resolve the default).
- Resolved with `mise --silent --cd <root> [--env <name>] env --json` and
  `... ls --json --current`, executed as an argv through the Local backend with a 30 s timeout.
- mise absent → `:mise_unavailable` (with remediation). A tool the project config requests but mise
  has not installed (`installed: false`, source under the root) → `{:missing_tools, name, tools}`.
- `MISE_ENV=<name>` is included in the resolved env (empty for `default`).
- Fingerprint = SHA-256 of the sorted `{tool, version || requested_version}` list (the **resolved**
  installed version first, so a prefix pin moving from 1.18.3 to 1.18.4 changes it), falling back to
  hashing the raw `ls` output when it cannot be parsed.
- mise never runs in an untrusted run. Its `[env]` values are configuration, not a secret store.

### Executor, policy, cache

- `Executor.run_pipeline/3` accepts `:pipeline_image` / `:pipeline_environment`; legacy
  `opts[:image]` / `ctx[:image]` still name a pipeline image.
- After `Preflight`, the environment plan is built for runnable stages and hooks. An error fails the
  run with `{:error, {:execution_unavailable, reason}, []}` after `pipeline_started` and before any
  `stage_started`.
- The plan lives on `ctx.environment_plan`; the options it was built with live on `ctx.environment_opts`.
  `execute/4` uses the stage's entry and puts `execution_backend`, `execution_image`,
  `execution_environment` and `toolchain_env` on the context before a session opens.
- A stage that was omitted from the plan (its `when:` was false at plan time) can become runnable once
  an earlier stage updates the store. Resolution then happens **at the stage boundary, after the skip
  check**, using `ctx.environment_opts`: the stage's own declaration is resolved and an error is a
  failed stage/run. It never inherits the previous backend or falls back to the host, and a still-skipped
  stage still pulls nothing.
- `Execution.resolve/2` refuses an explicit `Local` when an image is set
  (`{:image_requires_container, image}`), not only for untrusted contexts.
- `Execution.error_message/1` explains every new reason, including `{:stage, name, reason}` and
  `{:hooks, reason}`.
- `Executor.Env.process/2` layers `toolchain < secrets < pipeline < stage < step` for shell steps and
  shell hooks; `Env.resolve/2` is unchanged (conditions, cache inputs, and control payloads stay
  toolchain-free).
- `execution_environment: Environment.cache_identity(env)` is added to the cache inputs for shell
  steps only, and only when non-nil. The identity includes the image digest (or ref), toolchain name,
  toolchain fingerprint, and a stable hash of the resolved toolchain variables — a mise `[env]` value
  the step runs with changes the key. An imaged shell step's `cache_env` excludes `System.get_env()`
  and its `runtime` input (the image identity is the runtime). Module steps keep the host
  environment/runtime identity.

### Dry-run and CLI

`TinyCI.CLI.Run` passes `spec.image` / `spec.environment` into the run options, and for `--dry-run`
builds the plan with `pull: false, check_availability: false`. `TinyCI.DryRun.print_plan/3` shows,
for a non-default environment:

```
Environment: container image=<ref> digest=<id-or-unresolved>
Environment: host environment=<name> (<tool> <version>, …)
Environment: unresolved — <message>          (yellow)
```

A host stage with no declaration prints exactly what it printed before; a skipped stage prints only
its skip line. The CLI exits 0 for a dry run with unresolved environments.

## Deviations

- **Stage-boundary re-resolution for a flipped condition.** The plan only contains stages that were
  runnable when it was built. A `when:` that reads the store can become true after an earlier stage
  writes it, so `run_stage_or_skip/3` resolves the stage's own declaration at the boundary (after the
  skip check) when the plan has no entry, using the plan's options stored on the context. This closes
  the silent host fallback the first planning pass would otherwise leave: a stage never inherits a
  previous backend or the operator default. Resolution errors are raised inside the stage guard and
  therefore surface as a failed stage/run. `Environment.stage_environment/3` is the public seam.
- **Toolchain cache identity includes the resolved env.** `Environment.cache_identity/1` adds a
  stable SHA-256 of the sorted toolchain variables, because a mise `[env]` value the step receives
  through `Env.process/2` changes what it builds. Host-default identities are still `nil`, so existing
  host keys are unchanged.
- **Fingerprint uses the resolved tool version.** `Mise.version/1` now prefers the installed
  `version` over `requested_version`, so a prefix pin (`elixir = "1.18"`) resolving from 1.18.3 to
  1.18.4 changes the fingerprint and misses the cache. The requested version remains the fallback
  when no resolved version is present.
- **Per-stage backend plan.** The draft assumed one run-level backend. Reproducibility requires a
  stage declaration to replace the pipeline declaration, so the plan is per stage (and one run-level
  entry for hooks). `ctx.execution_backend`/`execution_image` are set per stage before its session
  opens.
- **`toolchain` field name.** The struct field for the `environment:` name is `:toolchain`, not
  `:env`, because `:env` holds the resolved variables (and `:environment` would shadow the DSL
  concept). `:image` remains the display ref, `:digest` the identity, `:run_ref` what is run.
- **Run by image ID.** Resolution inspects the image and starts containers by the local ID. A
  `@sha256:` reference keeps the declared digest as `digest`/cache identity but still runs the local
  ID as `run_ref`. `Container.open/1` refuses to `pull` an ID it can no longer find.
- **Untrusted all-imaged runs need no default image.** The draft's D1 table required a default image
  for every untrusted run. A run whose runnable stages all resolve to images (and whose shell hooks,
  if any, are covered by the pipeline declaration) now runs without one. The plan is only built for
  runnable stages, so a `when:`-skipped stage needs neither an image nor a runtime.
- **`environment "default"` semantics.** `default` means the repository's default mise config with
  `MISE_ENV` cleared; other names require `mise.<name>.toml` / `.mise.<name>.toml`. This check exists
  because `mise env -E typo` silently succeeds against the default config.
- **Mixed-scope replacement.** A stage `environment:` under a pipeline `image:` (and vice versa) is
  allowed and replaces the pipeline declaration wholesale. It is shown in the dry-run plan so the
  backend switch is visible.
- **LSP stale test.** `tiny_ci_lsp/test/tiny_ci/lsp/completion_test.exs` was missing `network:` in
  its stage-options expectation; it now also expects `image:`/`environment:`.
- **Cache identification of an imaged shell step.** The task text says "a Container
  shell step". The executor identifies that case by the resolved environment having
  an `image` (which selects Container in production), so an injected test backend
  with an image exercises the same cache path. A module step never qualifies.
- **Tagged stage errors.** Because `strict/1` names the failing stage, `run_pipeline/3` now returns
  `{:error, {:execution_unavailable, {:stage, name, reason}}, []}` for an unresolvable stage (and
  `{:hooks, reason}` for the hook phase). Two existing assertions were updated to the tagged shape;
  the CLI's remediation text is unchanged.
- **Plan and execution both evaluate `when:`.** `TinyCI.Stage.skipped?/2` is the single
  implementation used by the executor, the dry-run plan, and the environment plan, as required. In a
  real run that means a `when:` condition is evaluated once for planning and once at the stage
  boundary. A raising condition is treated as runnable during planning so the stage boundary still
  reports the failure as a failed stage (the pre-existing contract).
- **`pull: false` instead of `:if_present`.** The TDD bullet's `:if_present` is the `pull: false`
  behaviour: a missing local image resolves with an unresolved digest and no pull. No separate option
  was added.
- **`:backend` is a backend seam, not a policy override.** An injected backend still receives the
  stage's resolved image/availability check; it exists so tests can observe session specs without a
  runtime. An untrusted run with no declaration and an explicit non-Local backend uses that backend
  (as the pre-existing `Execution.resolve/2` allowed); Local is never accepted as a host fallback.
- **`environment:` integration test trust.** The `:mise` integration copies `.mise.toml` into a temp
  project. mise refuses untrusted config paths, so `Mise.resolve/2` accepts an `:env` option and the
  test trusts only the copied file (`MISE_TRUSTED_CONFIG_PATHS`). This seam is not used by the
  runner.
- **Matrix container smoke test.** Rootless Podman can race two fresh user namespaces; the matrix
  container test sets `max_parallel: 1` so it is deterministic while still proving both combinations
  use the stage's resolved image.

## Follow-ups

- Private-registry authentication and image allow-listing for hosted runs (M2 serve config).
- An environment lockfile: record resolved image digests and toolchain fingerprints alongside the
  pipeline, then verify them at run start.
- Manifest digests: the current identity is the local image ID. A shared cache across machines needs
  the registry manifest digest (or an explicit `@sha256:`), not a per-machine ID.
- Record the resolved environment (image ref, digest/ID, tools) in the run event stream and the
  attestation, so history states exactly what ran.
- A per-run mise cache: every run currently shells out twice; a process-level memo could be shared
  across runs when the config fingerprint is unchanged.
- `image:` for module steps requires the M4 runner model (running the runner itself in the image);
  until then module steps stay in the VM, as documented.
- `mix.lock`/lockfile checks for toolchain configs (mise lockfiles) are out of scope here.
