# M1.5-09 — Split `TinyCI.Executor` into a facade and focused modules

**Milestone:** M1.5 · **Size:** M · **Depends on:** — · **Status:** ⬜ Not started
**Written against:** commit `260a9ba` (2026-10-28)
**Blocks:** M1.5-04, M1.5-05

## Summary

`lib/tiny_ci/executor.ex` is 1,779 lines, and one module does all of this:

- run lifecycle (dispatcher, control plane, preflight, hooks, `run_finished`);
- environment planning per stage;
- stage ordering, both sequential and DAG levels;
- the stage boundary (crash guard, `when:`, breakpoints, sessions);
- matrix fan-out;
- the serial and parallel step fan-out;
- the step boundary (crash guard, breakpoints, retries);
- the cache wrapper and artifact persistence;
- the shell and module step bodies;
- event construction.

Every boundary the remaining M1.5 work touches is inside this one file:

- M1.5-04 needs a place to hang run ownership and cancellation.
- M1.5-05 replaces the level scheduler.

This task is a **behaviour-preserving split**. `TinyCI.Executor` keeps its public API (`run_pipeline/3`, `execute/4`) and becomes a thin facade over the run lifecycle. Each concern moves to its own module under `lib/tiny_ci/executor/`, and the dependency direction runs one way only (run → schedule → stage → steps → step → body).

The one design change is that stage ordering moves behind an **injected stage runner**. M1.5-05 can then replace the scheduler by swapping one module, and test it without running a single shell command.

## Why now

- M1.5-04 and M1.5-05 are the riskiest changes left before M2. Both would otherwise be written into the hardest file in the repo to read, and their diffs would be hard to review.
- The task files for those two already cite `executor.ex` line ranges that have gone stale (`M1.5-05` cites `:325-350` for code now at `:489-512`). The file is moving faster than the plans that describe it.
- No functions have to be redesigned. The seams already exist as private-function groups with clear comments. This is mostly moving code, which is cheap now and gets more expensive with every task that grows the file.

## In scope

1. **Characterization tests first** (see TDD plan 1). They pin the event stream and the results for a representative set of runs, before any code moves.
2. **Split the module** per the *Module map* below. Every function moves with its comments intact.
3. **Inject the stage runner.** `Executor.Schedule.run/3` takes a `run_stage` function, so it never calls `StageRunner` directly (see *Design*).
4. **Drop dead parameters.** `output_mode` is threaded through about ten step-level functions, but it is only read in `execute_parallel/4`, where it computes the line prefix. `run_step/5` ignores both `output_mode` and `prefix` (`executor.ex:1619`, `:1628-1632`), and `execute_matrix_stage/3` ignores `output_mode`. After the split:
   - `output_mode` stops at `Executor.StepGroup`;
   - `prefix` goes only as far as the `StepStarted` emission.
5. **Delete `TinyCI.Executor.start_link/1`** (`executor.ex:90`). Nothing calls it, because `TinyCI.Application` starts `{Task.Supervisor, name: TinyCI.TaskSupervisor}` directly. Check with `grep -rn "Executor.start_link" lib test` first.
6. **Fold repeated event fields into helpers.** Every step-scoped event repeats `run_id: run_id(ctx), timestamp: now(), stage: stage_name(ctx), matrix_combination: combination(ctx)`. Put builders in `Executor.Emit` that fill these. The event structs and their fields must not change.
7. Update the stale `executor.ex:` line references in `M1.5-04` and `M1.5-05`, and update the `README.md` project-structure tree.

## Out of scope

- Any behaviour change:
  - event types, fields or order;
  - console bytes;
  - result shapes;
  - exit codes;
  - store-merge semantics;
  - crash, abort or skip semantics.
- Readiness scheduling and the concurrency cap (M1.5-05). This task *pins* the current level-barrier behaviour; it does not fix it.
- Run ownership, the process tree and cancellation (M1.5-04).
- Turning the context map into a struct, or adding a step-invocation struct (see *Follow-ups*).
- Removing the `is_function(f, 1)` clause from `skip_step?/2`. Production never produces it, but about ten tests in `executor_test.exs` build function conditions, so removing it is a test rewrite, not a move.
- Moving the two `IO.puts(:stderr, …)` warnings (the filter warning and the artifact warnings) onto the event stream. That changes output; see *Follow-ups*.
- Editing any existing test file. The existing suite is the safety net and must pass **unmodified**.

`Callback`, `Crash`, `Driver` and `Env` are unchanged.

Naming: the modules are `StageRunner` and `StepRunner`, not `Stage` and `Step`. Those short names would clash with the `TinyCI.Stage`/`TinyCI.Step` structs whenever either is aliased, and the existing code pattern-matches `%TinyCI.Stage{}`. For the same reason the other two are `MatrixStage` (because of `TinyCI.Matrix`) and `StepArtifacts` (because of `TinyCI.Artifacts`).

### Dependency direction (must be acyclic)

```
Executor ──► Sinks
   │   └───► StageEnvironment ◄──────────┐
   ▼                                     │
Schedule ──(run_stage fun)──► StageRunner┘──► MatrixStage ──► StepGroup
                                   └──────────────────────────► StepGroup ──► StepRunner
StepRunner ──► StepCache (body fun) · StepArtifacts · ShellStep · ModuleStep
everything ──► Emit, Support
```

- `Schedule` never names `StageRunner`. The facade passes `&StageRunner.run/3`, which removes the only cycle a naive split would create: `execute/4` → stage, and the DAG → `execute/4`. Today `run_dag_stage/4` and `run_pipeline_sequential/3` call the public `execute/3` (`executor.ex:458`, `:606`).
- `StepCache.run/4` takes the step body as a function `(ctx -> %StepResult{})`. `StepRunner` passes its retry loop, so the cache never calls back into `StepRunner` by name.
- `MatrixStage` and `StageRunner` both call `StepGroup`, never each other the other way round. `StageRunner` → `MatrixStage` is the only edge between them.

### `Executor.Schedule` interface

```elixir
@type run_stage :: (TinyCI.Stage.t(), map(), Output.mode() -> StageResult.t())

@spec run([TinyCI.Stage.t()], map(), Output.mode(), run_stage()) ::
        {:ok, [StageResult.t()]} | {:error, term(), [StageResult.t()]}
def run(stages, ctx, output_mode, run_stage)

@spec filter([TinyCI.Stage.t()], [atom()] | nil) :: [TinyCI.Stage.t()]
def filter(stages, filter)
```

`run/4` chooses sequential or DAG with `DAG.dag_mode?/1`, as `run_stages_and_hooks/4` does today. M1.5-05 keeps this signature and replaces the body of the DAG branch. The `{:circular_dependency, _}` path from `DAG.build_levels/1` stays where it is.

### Visibility and docs

The moved functions become `def`, because they are now called across modules. Each new module gets an `@moduledoc` that says what it is for and starts with *"Internal to `TinyCI.Executor`; not a public API."* Each module's entry function gets an `@doc`. Helpers that are only public so a sibling module can call them get `@doc false`. Keep every existing comment next to the code it explains: those comments carry the invariants.

## TDD plan

This is a refactor, so the "red" step is replaced by **pinning**. Tests are written against the current code, must pass before anything moves, and must still pass after every move. Land the work as a short series of commits, keeping the suite green at each one (see *Commits*).

0. **Baseline.** Run `mix test` and record the count (1840 tests, 11 excluded at `260a9ba`). Then run `mix xref graph --format cycles` and record its output; it has 6 cycles today, including `executor/driver*`.

1. **Characterization: `test/tiny_ci/executor/characterization_test.exs`.** Use `extra_sinks: [{TinyCI.TestSink, pid: self()}]`, `console: false` and `record: false`. Normalize each event to a tuple of its type plus its stable fields (stage, step, status, reason, combination, attempt, total, line, allowed_failure, cache result), dropping `run_id`, `timestamp`, `duration_ms` and `seq`. Assert three things:
   - **ordered sub-sequences per entity**: for each stage, step and matrix combination, the exact sequence of its events;
   - **exact global order** wherever the run is serial;
   - the **normalized result tuple** (`durations` zeroed).

   Do not assert global order across parallel siblings, because it is nondeterministic. Cover these scenarios:
   - a sequential pipeline: a serial stage with a step skipped by `when:`; a step that fails once and then passes (`retry: 1`, with a counter file under `@tag :tmp_dir`); a stage that halts on failure; and a later stage that never starts;
   - a parallel stage with an `allow_failure: true` step;
   - a DAG `A → {B, C}`, where `B` fails and `D needs: [:B]` is skipped with `"dependency failed"`;
   - a 2×1 matrix stage whose module step writes the store, checking `store_delta` and the per-combination `artifacts_dir`;
   - a cached shell step run twice: a miss and then a hit, with a `CacheLookup` on both;
   - a module step that raises: one failed step, and the run completes;
   - `on_success`/`on_failure` hooks: their events come before `run_finished`;
   - standalone `execute/4` with no dispatcher on the context: the ephemeral dispatcher path.

   This is the test M1.5-05 will lean on too, so make the expectations readable literal lists, not a snapshot file.

2. **Scheduler characterization: `test/tiny_ci/executor/schedule_test.exs`.** Write it against `Executor.Schedule.run/4` with a **fake `run_stage`** that sends `{:started, name}` to the test and blocks on `{:release, name}`. Use no shells and no `Process.sleep`. Cover:
   - sequential halts on the first `:failed`, and `:aborted` maps to `{:error, {:aborted, name}, _}`;
   - an aborted stage dominates a failed one in the DAG result;
   - a failed stage blocks its transitive dependents (they get `StageSkipped "dependency failed"`);
   - **the level barrier**: in `A → {B, C}; D needs C`, `D` does not start until `B` is released. Tag this test `@tag :level_barrier` and add the comment `# M1.5-05 inverts this assertion`.
   - `filter/2` drops filtered-out `needs:` and warns on stderr (`ExUnit.CaptureIO`).

   This test cannot be written until step 6 creates the module. Write it first in that commit, against the new module.

3. **Leaf modules: `Support`, then `Emit`.** These are pure moves. Add doctests for `Support.resolve_working_dir/2`. Add a test in `test/tiny_ci/executor/emit_test.exs` checking that a step event built in a matrix context carries `matrix_combination`, and one built outside a matrix carries `nil`.

4. **Bodies: `ShellStep`, `ModuleStep`, `StepArtifacts`, then `StepCache`.** Add a direct test for `StepCache.run/4` with an untrusted context: the body is called exactly once and no `CacheLookup` is emitted. Today that is only checked indirectly.

## Pitfalls

- **Crash boundaries must cover exactly what they cover today.** `run_stage_guarded/3` wraps `when:` evaluation *and* the stage body; `run_step_guarded/5` wraps cache restore, the body, artifact copy and control. When code moves into another module, the call must stay *inside* the `rescue`/`catch`. A function moved out from under a `try` turns a failed step back into a crashed run, which undoes M0-01. The characterization test's "module step raises" case catches some of this, not all, so review the guards by hand.
- **The group leader.** All three spawn sites (DAG stages, parallel steps, matrix combinations) call `Process.group_leader(self(), caller_gl)`. That is what keeps module IO captured and the console intact. Keep it at each site.
- **Session lifetime.** A regular stage opens **one** session that spans the body, the `after:` boundary and a control `retry` (`review_stage/3`). A matrix stage opens one session **per combination** instead. Do not "simplify" these into one shape.
- **Environment resolution happens after the skip check.** `ensure_stage_environment!/2` runs only once a stage is known not to be skipped, so a skipped stage never pulls an image (`run_stage_or_skip/3`). Keep the order.
- **Overrides on `store_data`.** The control overrides from `Control.checkpoint/2` are merged into `StepResult.store_data`, and that is how an operator's edit escapes a parallel branch. Keep `merge_overrides/2` on the result path.
- **Retry bypasses the cache.** A control `retry` sets `no_cache: true` on the context (`review_step/6`). Keep that line next to the retry, not in `StepCache`.
- **Masking happens twice, on purpose.** `ModuleStep` masks `captured <> output`, and then masks again when it builds the result. Do not deduplicate this in the move. `live_line_events?/1` must stay the gate for multi-line secrets.
- **The ephemeral run id.** The standalone `execute/4` path sets `run_id` with `Map.put_new/3`; do not overwrite an existing id.
- **Aliasing.** `alias TinyCI.Executor.StageRunner` plus `alias TinyCI.Stage` is fine. `alias TinyCI.Executor.Stage` would not be, which is why the modules are not named that way.
- **Don't move tests.** `executor_test.exs` is 2,510 lines. Splitting it is tempting but is a separate change, because the unmodified suite is what proves this one.

## Follow-ups

- **A step-invocation struct.** After this task, step functions still take `(step, ctx, prefix, working_dir, index)`. A `%StepRun{}` would make the signatures honest.
- **Type the executor's context keys.** The executor adds about 15 keys to the open context map (`:events`, `:control`, `:control_serial`, `:stage_env`, `:stage_name`, `:matrix_combination`, `:execution_session`, `:environment_plan`, …). A documented type, or a struct, would make M1.5-04's per-run state explicit.
- **Warnings on the event stream.** `Schedule.filter/2` and `StepArtifacts` still write warnings with `IO.puts(:stderr, …)`, outside the event stream (ROADMAP principle 3). Emitting them as events changes output, so it belongs with M1.5-04 or the UI work.
- **The `is_function(f, 1)` branch of `skip_step?/2`.** Production never produces a function condition, so the branch exists only for tests. Rewrite those tests to use quoted conditions, then delete it (carried over from M1.5-08).
