# M1.5-06 — A `RunStore` port so local and hosted share the run model

**Milestone:** M1.5 · **Size:** M · **Depends on:** M0-06 · **Status:** ⬜ Draft
**Written against:** commit `e9f5b8c` (2026-10-10)

## Summary

Run history today is a directory tree under `$XDG_DATA_HOME/tiny_ci/runs/<project_id>/<run_id>/`
with `events.ndjson` + `meta.json`, read and folded by `TinyCI.Runs` / `Runs.Projection`. That is
the right local-first design. It will not hold up as the server's store: a hosted instance needs to
list across many repos, filter by status/branch/time, retain/prune by policy, and answer those
queries without scanning every run directory.

The risk is not "files are slow" — it is **shipping a server that reaches around `TinyCI.Runs` into
the filesystem**, creating a second, server-only data path (the thing invariant **I1** forbids). This
task prevents that by defining the storage **port** now and putting the existing files
implementation behind it, so the server can later add a queryable backend without touching consumers.

**Core stays zero-dependency.** No SQLite dependency is added here; the requirement is the *seam*, not
the engine.

## Why now

- It is cheap and purely structural while there is exactly one consumer (`TinyCI.Runs`).
- It lets the server's storage choice (SQLite vs files vs something else) be made in M2 *without*
  reworking every caller.
- It is a prerequisite for the "one event stream, any view is a fold" principle
  (`ROADMAP.md:61-63`) to hold in a hosted deployment.

## In scope

1. `TinyCI.RunStore` behaviour in core — the operations consumers actually need, e.g.:
   `put_meta/3`, `append_events/2`, `get/2`, `list/1` (filter: project, status, since, limit),
   `project/2` (or `fold/3`), `prune/2`, `mark/3`. Exact surface decided in Design; keep it minimal
   — every function must have a real caller.
2. `TinyCI.RunStore.Files` — the current behaviour moved behind the port unchanged (same on-disk
   layout, so existing data keeps working).
3. `TinyCI.Runs` becomes a facade over the configured store
   (`config :tiny_ci, :run_store, TinyCI.RunStore.Files`), with **no behaviour change** and all
   existing `runs_test.exs` / `projection_test.exs` green.
4. `TinyCI.Runs.mark/3` and the statuses from M1.5-04 expressed on the port.
5. A short decisions note: what a future `RunStore.SQLite` would have to satisfy (the acceptance test
   is that a second implementation can pass the same contract suite).
6. An **optional**, `@moduletag`-excluded contract suite shared by any store implementation
   (`TinyCI.RunStoreCase` under `test/support/`), so a second backend is cheap to validate later.

## Out of scope

- Adding SQLite/`exqlite` or any dependency (that belongs to the server app in M2).
- Migrating existing run data between layouts.
- The web/JSON API (M2-07) — this is the storage seam only.
- Changing event or projection schemas.

## Read first

- `lib/tiny_ci/runs.ex`, `lib/tiny_ci/runs/recorder.ex`, `lib/tiny_ci/runs/projection.ex` — the
  current read/write paths and the exact operations to lift.
- `lib/tiny_ci/cli/runs.ex`, `lib/mix/tasks/tiny_ci.runs.ex` — the consumers.
- `lib/tiny_ci/events/dispatcher.ex` — how the recorder appends events.
- `lib/tiny_ci/artifacts.ex` — artefacts stay on the filesystem regardless of the run store (note
  the boundary: run metadata/history moves, artefacts do not).
- `test/tiny_ci/runs_test.exs`, `test/tiny_ci/runs/projection_test.exs` — the contract to preserve.

## Design notes

- Keep the port **query-shaped, not table-shaped**: `list(filter)` and `fold(run_id)`, not
  `select_where`/raw rows. The files backend implements `list(filter)` by scanning `meta.json`; a
  SQLite backend implements it with an indexed query. Both satisfy the same behaviour.
- Pass a `filter` struct (a small map/struct), so adding `:branch` or `:since` later does not change
  arities.
- `project/2` / `fold/3` must remain the single way to build a run view, so the console, CLI, and a
  future UI cannot diverge (principle 3).
- Do not leak `File.*` out of `RunStore.Files`; consumers should be unable to tell which backend is
  configured.

## Acceptance criteria

- [ ] `TinyCI.Runs` performs no direct filesystem access; it goes through the configured
      `RunStore`.
- [ ] `RunStore.Files` reproduces today's on-disk layout, so existing runs still list and project.
- [ ] A store can be swapped via `config :tiny_ci, :run_store` and all consumers follow.
- [ ] The shared contract suite exists and `Files` passes it.
- [ ] Core gains no dependency.
- [ ] Artefacts are explicitly out of the port and still filesystem-backed.

## Pitfalls

- Do not over-model. If a function has no caller today, leave it out; the port can grow.
- Keep the recorder's append hot path allocation-free-ish; a port call per event is fine, but do not
  re-read the whole file per append.
- Resist putting artefact paths into the store; only history/metadata moves.
