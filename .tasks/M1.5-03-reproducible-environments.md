# M1.5-03 — Reproducible environments for local and hosted

**Milestone:** M1.5 · **Size:** M · **Depends on:** M1.5-01, M1.5-02 · **Status:** ⬜ Draft
**Written against:** commit `e9f5b8c` (2026-10-10)

## Summary

The second reason a team adopts GitHub Actions over a hand-rolled runner is reproducibility: the job
gets a *pinned* toolchain, the same one every time, on every machine. tiny_ci currently has no
answer to "which Go version does this job get?" — the answer is "whatever is installed on the host,"
which is runner drift by construction.

This task adds an explicit environment to a pipeline: an optional **`image:`** (an OCI reference) at
pipeline or stage level, plus a small **`environment:`** vocabulary for the common non-container
case. When `image:` is set, the step runs in that image in **both** modes, so a pipeline developed on
a laptop and one run on the server share the toolchain. Combined with M1.5-02, this closes the
local/hosted reproducibility gap.

## Why now

- It is the other half of "the pipeline you run on your laptop is the same one the server runs"
  (`ROADMAP.md:14-15`); M1.5-01/02 give the same *code path*, this gives the same *environment*.
- Cache identity (`TinyCI.Cache`) must include the image **before** it is relied on: otherwise a
  cached build from `elixir:1.18` would be reused for `elixir:1.19`. Getting this in early avoids a
  correctness bug that is very hard to debug later.
- Hosted runners (M4) become "a machine that can run containers," not "a machine with every
  toolchain pre-installed."

## In scope

1. `image` at pipeline and stage level, added to `TinyCI.DSL.Spec` + `Validator` + README + LSP
   (the spec drives it). Stage overrides pipeline. In `TinyCI.DSL.Spec` terms these are two
   entries: a new **directive** in `@directives` with `contexts: [:top_level]` (file scope, beside
   `name`, `env`, `secret` — e.g. `image "elixir:1.18"`), and a new **option** in `@stage_options`
   (`stage :build, image: "..."`). The same applies to `environment`.
2. Executor/backend wiring: the resolved image goes on the stage's `SessionSpec.image` (M1.5-01),
   and `TinyCI.Execution.Policy` selects the Container backend whenever an image is set, trusted or
   not (D1 table). If `image:` is set and no container runtime is available, fail with a clear error
   (never silently run on the host — that would be a reproducibility lie).
3. `environment:` — a small, explicit alternative for trusted local work and hosts without
   containers: a named toolchain resolved from `mise`/`.tool-versions` (the repo already dogfoods
   `.mise.toml`). This is deliberately *not* a package manager and *not* a YAML block; it is a
   pointer the runner can honour locally and that the server can translate to an image (or reject).
4. **Cache identity:** add the resolved `image:` (digest, once available) and `environment:` to the
   cache key inputs in `TinyCI.Cache`.
5. `--dry-run` prints the resolved environment per stage (so a user can see the toolchain before
   running).

## Out of scope

- Building images. tiny_ci consumes images; it does not build them.
- A full Nix/Devbox integration (a plausible future; out of scope).
- Registry auth for private images (note for M2/serve config).
- Changing module-action execution. Module steps in a stage with `image:` still run in the
  runner's VM, not in the image; document this. (`image` is a stage option, so there is no
  per-step `image:` to reject.)

## Read first

- `lib/tiny_ci/dsl/spec.ex`, `lib/tiny_ci/dsl/validator.ex`, `lib/tiny_ci/dsl/interpreter.ex` — adding
  a directive and threading it onto `%Stage{}` / the spec.
- `lib/tiny_ci/cache.ex` — how the cache key is assembled (`cache_identity`/inputs) — this is where
  the image joins.
- `lib/tiny_ci/execution/backend/container.ex` (M1.5-02) — where the image is consumed.
- `lib/tiny_ci/dry_run.ex` — the plan printer.
- `.mise.toml` — the existing toolchain pin; the `environment:` vocabulary should feel native to it.

## Design notes

- Prefer image **digests** over tags in cache identity once resolved (`docker inspect`), so
  `latest`-style drift is caught. Record both the ref (for display) and the digest (for the key).
- Resolution is per stage and immutable for the run: a stage's image is resolved once, then every
  session opened for that stage (its steps, and each matrix combination's session — D3) uses the
  same digest. The pipeline-level image also feeds the hook session.
- `environment:` and `image:` are mutually exclusive on the same stage; validator rejects both.
- Keep the resolution logic pure and testable: a `TinyCI.Environment.resolve/2` returning a struct
  `%{image: ref | nil, digest: sha | nil, env: name | nil}` that dry-run, executor, and cache all
  read.

## TDD plan (to be finalized)

1. DSL tests — `image:` and `environment:` accepted at both levels; stage override wins; both set is
   rejected; bad values rejected.
2. `test/tiny_ci/environment_test.exs` — `resolve/2` returns the expected struct; digest is included
   when available (fake the inspect via a seam, do not require Docker).
3. `cache_test.exs` — two runs differing only in `image:` produce **different** cache keys; same
   image, same key. This is the regression guard.
4. `dry_run` test — the resolved environment appears in the plan.
5. Container-tagged integration (excluded without a runtime) — `image:` causes `elixir -v` inside the
   container to report the pinned version.

## Acceptance criteria

- [ ] `image:` at pipeline and stage level runs the stage's steps in that image (both modes).
- [ ] `image:` with no container backend is an explicit failure, not a host fallback.
- [ ] Cache identity changes when `image:` (or its digest) changes.
- [ ] `--dry-run` shows the resolved environment.
- [ ] `environment:` resolves a `mise`/`.tool-versions` toolchain for local work.
- [ ] README DSL reference and `docs/execution-model.md` document both directives.

## Pitfalls

- Do not resolve the image digest on every step; resolve once per run (it may require a registry
  round-trip).
- A shallow integration that only checks the flag was passed will pass while the step still runs on
  the host — assert something only the image can satisfy (`elixir -v` output, a file that exists in
  the image and not on the host).
- `environment:` must degrade clearly when `mise` is absent, again without host fallback surprises.

## Docs
