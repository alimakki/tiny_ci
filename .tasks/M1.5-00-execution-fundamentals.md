# M1.5 — Execution fundamentals (gates M2)

**Milestone:** M1.5 · **Status:** ⬜ Draft (not scheduled)
**Written against:** commit `e9f5b8c` (2026-10-10)

> **These are draft tasks.** They are written to be reviewed and sharpened before any of them is
> picked up — the designs below are proposals, not settled decisions. Once the *Decisions* section
> is agreed, each task gets the same red→green treatment as M0 (full TDD plan, acceptance criteria,
> pitfalls) per [`CONVENTIONS.md`](CONVENTIONS.md).

## Why this milestone exists

M0 finished the runner's *correctness* fundamentals. M1.5 finishes its *execution-model*
fundamentals, and the reason to do it now is a single requirement that has to be designed in, not
bolted on later:

> **The same runner must run the pipeline on a laptop and on a server, and a pipeline that runs on
> one must run the other.** No server-only execution paths, no "works locally, not in CI" drift.

Everything M2–M4 builds (queue, webhooks, UI, runners) is a thin layer over this. If the execution
model is wrong, every milestone above inherits the mistake. So M1.5 is the last chance to fix the
shape of execution cheaply, while there are still no users.

Two gaps make the current shape wrong for that requirement:

1. **The execution boundary is implicit and host-only.** Shell steps call `TinyCI.Output.run_cmd`
   directly, on the host, unsandboxed (`docs/reliability.md:29`). There is no seam where a
   different *where-does-this-process-run* backend can be plugged in, and no place a server could
   say "run this step in the job's image."
2. **A run is not a process tree.** `TinyCI.Application` supervises only a `Task.Supervisor` and a
   `Registry`; the dispatcher and control server are started bare, and parallel work is unlinked
   tasks. The ROADMAP's own table claims "a run in flight = one supervised process tree"
   (`ROADMAP.md:23`) — that claim is not true yet (it is M2-01). Without it there is no clean
   cancellation and no place to hang per-run state.

## The two invariants

Every task below serves one or both. They are the acceptance bar for the milestone.

- **I1 — Local/hosted parity.** A `%PipelineSpec{}` executed by `TinyCI.Executor` produces the same
  structured result and the same ordered event stream regardless of *mode* (`:local` or `:server`)
  and regardless of which execution backend is selected. Mode changes *defaults and policy*, never
  the execution code path.
- **I2 — One run, one supervised tree, one event stream.** A run is a supervised process tree that
  can be cancelled hard, and every observable thing about it is an event on its stream (which is
  what makes both the console *and* a future web UI presentations of the same data).

### D1 — Trust belongs to the invocation, never to the pipeline (settled)

A pipeline file is exactly what an untrusted pull request controls, so it cannot be allowed to
declare itself trusted. There is **no `trust` DSL directive**.

- Every run carries `ctx.trust :: :trusted | :untrusted`, set by the entrypoint that started it.
- **Mode supplies the default**: `:local` → `:trusted`, `:server` → `:untrusted`. This is the
  "mode changes defaults and policy" half of I1; the code path is the same either way.
- **Local override:** `tiny_ci run --isolate` makes the run `:untrusted` (for trying a stranger's
  branch, or reproducing a server run exactly).
- **Server override (M2):** a per-repository `trust: :trusted` in the server config (M2-07). A
  run triggered by a pull request from a fork is `:untrusted` regardless of that setting (M2-04),
  and an untrusted server run resolves no secrets (M2-06). M1.5 only provides `ctx.trust`; those
  three rules are requirements recorded for M2.
- Backend selection is one pure function, `TinyCI.Execution.Policy.backend/2` (M1.5-02):

  | trust | `image` set? | backend |
  |---|---|---|
  | trusted | no | Local (host) — today's behaviour, unchanged |
  | trusted | yes | Container (error if no runtime — M1.5-03) |
  | untrusted | yes | Container |
  | untrusted | no | Container with the operator's `default_image`; error if none is configured |

  An untrusted run never gets the Local backend, and nothing ever silently falls back to the host.

Consequence: every existing local pipeline keeps running on the host with zero configuration, so
the M1 gate (a shell-only pipeline on a machine with no Erlang — and no Docker) still holds.

### D2 — In an untrusted run, no repo-controlled code executes on the host (settled)

Isolating shell steps is not enough; the boundary has to cover every way repository content can
become code. The inventory, as of `e9f5b8c`:

| Repo-controlled input | Today | Untrusted run (M1.5) |
|---|---|---|
| Pipeline file (`tiny_ci.exs` / `.tiny_ci/pipeline.exs`) | Interpreted against an allowlist, never compiled (`dsl/interpreter.ex`) | Unchanged — already safe by design |
| Shell steps | `sh -c` on the host | Run in the container session (D3) |
| Shell hooks (`on_success`/`on_failure`) | `sh -c` on the host (`hooks.ex:80`) | Run in a hook session (D3) |
| Module hooks | `module.run/2` in the runner's VM | Same rule as module steps (next row) |
| Module steps | Run in the runner's VM if the module is loaded (`:first_party`/`:local` inline, `:third_party` under Bubblewrap/Seatbelt) | Only `:builtin` actions (shipped with tiny_ci) run. Any other module step **fails closed** with a clear error. An untrusted run never compiles or loads repository code. |
| `mix.lock` | **Evaluated** with `Code.eval_string` (`action/lockfile.ex:52`) | Parsed as data only — fixed for every run, not just untrusted ones (M1.5-02) |
| Cache and artifact content | Copied as files (`cache.ex`, `artifacts.ex`) | Unchanged — data, not code |

Third-party module actions stay supported in *trusted* runs through the existing sandbox driver.
They are refused in untrusted runs because their dependency code has to be compiled and loaded on
the host before the sandbox ever sees it (`docs/reliability.md:29-32`). Running the whole runner
inside the container — which would lift this restriction — is the M4 runner model, not M1.5.

### D3 — One container session per stage (settled)

A container per *step* loses everything a toolchain keeps outside the workspace (`$HOME` caches,
installed tools, `go` and `npm` state), and makes cancellation and image resolution per-step
problems. tiny_ci follows the CI convention of one environment per job; a stage is our job.

- A **session** is one long-lived container: `docker run -d --init` with a keepalive, created when
  a stage starts and removed (`docker rm -f`) when it finishes, in an `after` path.
- Each step is a `docker exec` into the stage's session, so steps share `$HOME`, installed tools,
  and the container filesystem. Parallel steps are concurrent `exec`s. Each matrix combination gets
  its own session. Hooks get a hook session built from the pipeline-level image.
- The container's root filesystem is writable (it dies with the session); the workspace is
  bind-mounted read-write at `/workspace`; nothing else from the host is mounted.
- **Network is stage-level** (a container's network is shared by its steps), and **on by default**:
  nearly every real pipeline fetches dependencies, and the threat the boundary must stop first is
  host compromise. `network: false` on a stage runs it with `--network=none`. Egress filtering is a
  documented non-goal for M1.5.
- Resource limits (`--memory`, `--cpus`, `--pids-limit`) apply per session, from operator config.
- Step timeout and cancellation kill the step's process group *inside* the container (killing the
  `docker exec` client does not); `docker rm -f` on session close is the backstop. The run
  (M1.5-04) tracks open sessions so cancelling a run closes all of them.

### D4 — Backends spawn and report lines; sinks render (settled)

Today `TinyCI.Output` prints as a side effect, which is wrong for a server and would bake the
console into every backend. M1.5-07 lands first and makes `Output` emit lines instead of printing.
M1.5-01 then defines the backend contract on top of that:

- A backend **spawns processes and reports output lines** to an `on_line` callback; it never
  writes to stdout or the console.
- The executor's callback emits `StepOutputLine` events, and the console sink renders them. So
  streaming vs buffered, `[prefix]`es and redaction never reach the backend.
- The contract is session-shaped (`open/1`, `exec/3`, `close/1`) so the container backend fits
  without changing callers. For the Local backend, `open` and `close` do nothing.

M1.5-01 therefore depends on M1.5-07.

### D5 — What is a reproducible environment? (`M1.5-03`, proposal)

An optional `image:` (OCI ref) at pipeline/stage level; when set, a stage runs in that image in
*both* trust levels (D1), so local and hosted share the toolchain. Host execution remains the
zero-config default for trusted local work.

### D6 — What is the run store? (`M1.5-06`, proposal)

Keep the lean core zero-dep; define a `TinyCI.RunStore` port in core with the existing files
implementation behind it, and let the server app add a queryable SQLite backend later. Do **not**
add a runtime dependency to core now.

### D7 — Does core get a run supervisor, or does the server? (`M1.5-04`, proposal)

**Core.** The CLI should get the same supervised run, because that is the only way I1 stays honest
and M2-01 becomes pure wiring.

## The gate

M1.5 is done when **all** of these hold, and M2 does not start until they do:

- [ ] A pipeline with `image:` produces the same `elixir -v` / `go version` output run via the CLI
      locally and via a future server entrypoint (I1) — demonstrated by a test that drives both
      entrypoints through the same `TinyCI.Runner`.
- [ ] An untrusted run (the `:server` default, or `tiny_ci run --isolate`) executes no
      repo-controlled code on the host (D2): steps and hooks run in container sessions, non-builtin
      module steps are refused, `mix.lock` is never evaluated, and with no container runtime the run
      fails closed. A trusted local run behaves exactly as today.
- [ ] Cancelling a run leaves no OS process of that run alive (`pgrep` proof), and the run's process
      tree is supervised (a crash in the tree is reported, not lost).
- [ ] A stage starts the moment its `needs:` are satisfied (no level barrier), and a global
      concurrency cap bounds total concurrent OS steps.
- [ ] The console output guarded by `console_test.exs` / `reporter_test.exs` is unchanged after the
      listener is retired, and a run can be reconstructed entirely from its event stream.

## What M2-01 becomes

Once M1.5-04 lands, `M2-01` shrinks to: point the server's facade (`TinyCI.Server.Runs`) at the core
`TinyCI.RunSupervisor` / `TinyCI.Run`, add the `EventBus` as an extra sink, and wire HTTP. The
`OSProcesses` registry, `TinyCI.Runner`, `project_id` override, and `Runs.mark/3` it currently
specifies all move into core under this milestone. **M2-01 must be re-read and trimmed against the
code once M1.5 lands** (per CONVENTIONS, record deviations rather than guessing).
