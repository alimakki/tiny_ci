# M1.5-02 — Untrusted-run isolation: trust policy and container sessions

**Milestone:** M1.5 · **Size:** L–XL · **Depends on:** M1.5-01 · **Status:** ✅ Done (2026-10-18)
**Written against:** commit `e9f5b8c` (2026-10-10)

## Summary

The single largest gap between tiny_ci and a real CI is the security boundary. `docs/reliability.md`
is honest about it: *"shell commands execute on the host… Do not execute untrusted PRs"*
(`docs/reliability.md:29-32`). But running untrusted code is not an edge case for CI — it is the
job. The existing Bubblewrap/Seatbelt sandbox only covers Elixir **module** actions, so it does not
help the Go/JS/Rust teams the ROADMAP explicitly wants to serve (principle 7).

This task implements decisions **D1–D3** from [M1.5-00](M1.5-00-execution-fundamentals.md):

- **D1:** trust comes from the invocation (`ctx.trust`), never the pipeline; a pure policy maps
  trust + image to a backend; `tiny_ci run --isolate` makes a local run untrusted.
- **D2:** an untrusted run executes no repo-controlled code on the host — shell steps and hooks run
  in containers, non-builtin module steps are refused, and `mix.lock` is parsed, never evaluated.
- **D3:** a **container backend** with one long-lived session per stage, steps as `docker exec`.

A trusted local run — the default — behaves exactly as today.

## Why now

- It is the difference between "a local task runner" and "CI." Everything in the ROADMAP's pain table
  (`ROADMAP.md:37-51`) assumes this is solved.
- It must be designed together with M1.5-01 (the seam) and M1.5-03 (`image:`), before code assumes
  host execution everywhere.
- Without it, M2's server is unusable for anything but fully-trusted repos, which removes most of
  the reason to build a server.

## In scope

1. ✅ **Stop evaluating `mix.lock` (landed first, independently).** `TinyCI.Action.Lockfile.parse/1`
   runs `Code.eval_string` on the repository's `mix.lock` (`action/lockfile.ex:52`), which is host
   code execution for anyone who controls the file. Replace it with `Code.string_to_quoted/2` and
   accept only literal terms (maps, tuples, lists, strings, atoms, numbers); anything else is
   `{:error, :not_a_lock_map}`. Stop creating atoms from untrusted keys (`String.to_atom` in
   `to_app/1`): keep app names as strings, or bound atom creation. This applies to every run, not
   just untrusted ones.
2. **`TinyCI.Execution.Policy`** — `backend(ctx, image)` implementing the D1 table exactly; pure, no
   I/O beyond the injected availability probe. An untrusted run never gets Local; there is no
   silent fallback. Plugged into the single place M1.5-01 chooses a backend.
3. **`--isolate`** on `tiny_ci run` / `mix tiny_ci.run`: sets `ctx.trust` to `:untrusted`. Help
   text says what it does and what it requires. Operator config:
   `config :tiny_ci, :default_image` (no built-in default), `:container_runtime`
   (`:auto | :docker | :podman`), `:container_limits` (`memory`, `cpus`, `pids`).
4. **`TinyCI.Execution.Backend.Container`** implementing the M1.5-01 contract per D3:
   - `open/1`: `docker run -d --init` (or `podman run`) with the entrypoint overridden by a
     keepalive (e.g. `tail -f /dev/null`); `--user <host uid>:<host gid>`; the workspace
     bind-mounted read-write at `/workspace`, nothing else mounted; `--network=none` when the
     stage sets `network: false`, the default bridge otherwise; limits from config; a
     `tiny_ci.run_id=<id>` label.
   - `exec/3`: `docker exec` with `-w` (the step's `working_dir` mapped under `/workspace`) and an
     explicit `-e` per variable — only pipeline/stage/step env, `TINY_CI_*` variables, and
     declared secrets; the host environment is never passed through. Each step runs under a small
     wrapper that puts it in its own process group and records the group id inside the container,
     so a timeout can `docker exec <id> kill -KILL -- -<pgid>` without touching sibling steps.
   - `close/1`: `docker rm -f`, idempotent.
5. **Sessions per D3:** one per stage, one per matrix combination, and one hook session for
   `on_success`/`on_failure` (pipeline-level image, else `default_image`). Parallel steps are
   concurrent `exec`s into the stage's session.
6. **Module code in untrusted runs (D2):** before the run starts, classify every module step and
   module hook with `TinyCI.Sandbox.Trust.classify/2`. Anything other than `:builtin` fails the run
   up front with a message naming the step and explaining why. Untrusted runs never compile or
   load repository code.
7. **`network:` stage option** (`@stage_options` in `TinyCI.DSL.Spec` + `Validator` + README):
   boolean, default `true`. Ignored by the Local backend (documented).
8. **Availability probe and error:** no usable runtime ⇒ `{:error, :no_isolation_backend}` with
   remediation text (install rootless Podman/Docker, or drop `--isolate` for a trusted run).
   Untrusted run with no `image` and no `default_image` ⇒ an explicit error naming both fixes.

## Out of scope

- Windows isolation (deferred; an explicit non-goal for now).
- Remote/Kubernetes orchestration (`ROADMAP.md:178`).
- Rootless setup on the developer's machine — document requirements, do not install them.
- The `image:` directive and digest pinning (M1.5-03). This task consumes `SessionSpec.image`,
  falling back to `default_image`.
- Egress filtering or proxies (D3: a documented non-goal).
- Server-side trust rules: per-repo trust config (M2-07), fork PRs always untrusted (M2-04), no
  secrets for untrusted server runs (M2-06). They are recorded in D1.
- Running the whole runner inside the container, which would let untrusted runs use non-builtin
  module steps (the M4 runner model).

## Design notes

- Every container command is assembled as **argv**, never a shell string. The step's command is
  passed to `sh -c` inside the container, so quoting matches today's `sh -c` semantics exactly. An
  image without a POSIX `sh` (e.g. distroless) is an explicit error at `open/1`.
- `--user <uid>:<gid>` keeps files the steps write in `/workspace` owned by the invoking user on the
  host (rootful Docker otherwise leaves root-owned files). Rootless Podman maps users itself; probe
  and document the difference rather than assuming.
- `--init` reaps zombies in the long-lived session; without it, a busy stage accumulates them.
- The `tiny_ci.run_id` label makes leaked sessions findable: `docker ps --filter label=...` is how
  M1.5-04's cancellation and a startup sweep (for a runner that crashed mid-run) find containers.
- Killing a `docker exec` client does **not** stop the process inside the container. Timeouts kill
  the process group in the container (item 4); `close/1` is the backstop.
- Fail closed is the whole point: every "can't isolate" path is an error, and each is tested.

## Pitfalls

- Rootless Docker vs Podman vs Docker Desktop differ on flags (`--pids-limit`, cgroups, user
  mapping). Probe capabilities rather than assuming.
- Never mount the Docker socket, `$HOME`, or the cache directory into a session. Cache restore and
  save stay host-side operations on the workspace.
- Keep the exclusion honest: a host without a container runtime must *skip* these tests loudly, not
  pass them silently (the existing sandbox suites set the precedent).
- A test that only checks a flag was passed will pass while the step still runs on the host. Assert
  something only the container can satisfy (a file that exists in the image and not on the host).

## Deviations

### Part 1 — `mix.lock` (landed)

Item 1 landed on its own, as the milestone ordering requires ("the `mix.lock` fix … should land
first of all"). Items 2–8 landed later in Part 2.

- Atom safety goes further than "keep app names as strings": the parser uses a
  `:static_atoms_encoder`, so no atoms are created from lockfile-controlled names — not only the
  keys. That also closes atom-table exhaustion through value positions and quoted keyword keys
  (the common `mix.lock` spelling), which keeping string keys alone would not.
- Hex entries whose `version`/`checksum`/`repo` are not binaries are rejected as
  `{:error, :not_a_lock_map}`: a crafted numeric checksum would otherwise crash the audit
  formatter's `String.slice/3`, and a non-string version would crash message interpolation.
- Every parse failure — syntax error, non-literal term, non-UTF-8 bytes, malformed entry — collapses
  to `{:error, :not_a_lock_map}`, so callers fail closed on a single, uniform reason. The CLI
  reports it with a specific message instead of a bare `Error: :not_a_lock_map`.
- Malformed or unknown non-hex entries (e.g. a `:git` tuple with a non-string ref) degrade to an
  `:other` entry with safe fields, as before; only hex entries are strict, because only hex fields
  are consumed as pinned data (compared, sliced, interpolated).
- `TinyCI.Action.Resolver` now looks up app names with `Atom.to_string/1` (the lockfile map is
  string-keyed); its `@locks` test fixtures moved to string keys.

### Part 2 — policy, containers and untrusted loading (landed)

- **Policy shape.** `TinyCI.Execution.Policy.resolve/3` returns the backend *and* the
  resolved image; `backend/3` returns only the module. `TinyCI.Execution.resolve/2` stores
  both on the context so sessions cannot drift from the run's decision.
- **No-load preflight.** The task text said pre-flight classifies modules; doing that with
  `Code.ensure_loaded/1` would itself load repository code. `Trust.classify/2` gained
  `load: false` (unloaded ⇒ `:unknown`, refused), and pipeline loading takes
  `load_actions: false` through `Discovery`, `Interpreter`, and `Action.validate_spec/2`.
  Untrusted attestation audits use the same no-load path.
- **Container process groups.** BusyBox `setsid` has no `-w`, and `docker exec … setsid`
  exits 0 when `setsid` forks. Each step therefore runs through a small outer shell:
  `setsid sh -c "$TINY_CI_WRAPPER"; status=$?; exit $status`, with the wrapper recording its
  own pgid. `open/1` requires `sh`, `cat`, `setsid`, and `sleep`.
- **Environment.** Step values are passed to the `docker exec` client's environment and
  forwarded by *name* with `-e NAME`, so secret values never appear in the host argv and
  host variables are not forwarded.
- **Hook sessions.** A hook phase opens one session for all of its shell hooks (module hooks
  do not force a session). If no session is permitted, each hook still reports its own
  failure through the normal hook events.
- **Runtime selection.** `:auto` prefers Docker then Podman, and both must answer
  `version`. Invalid `:container_runtime` values fail closed.
- **Working directories.** The executor's host `File.dir?` check is skipped for container
  sessions; the backend maps the directory under `/workspace` and reports a missing
  directory itself.
- **Tests.** `:container` is excluded when no runtime is available and otherwise runs
  (Docker here), using a pinned `alpine:3.22` image. Cold images are
  pulled explicitly before `run`; a start failure cleans up by a per-session
  label. The suite covers failed, timed-out, and hook runs. `:bubblewrap`/
  `:seatbelt` exclusions are unchanged.
- **Trusted runs and the operator default.** `default_image` is applied only to
  untrusted runs. A trusted run with no image still uses the host even when an
  operator has configured a default image.
- **Untrusted paths and cache.** Untrusted runs reject a `working_dir` outside
  the project root and skip cache restore/save entirely (those are host-side file
  operations driven by repository paths). `.git` is mounted read-only.
- **Condition env.** In an untrusted run, `when: env("NAME")` only reads the
  resolved pipeline/stage/step environment; it never falls back to the runner's
  host environment.
- **Mix caveat.** `mix tiny_ci.run --isolate` prints a warning: Mix has already
  loaded `mix.exs` and its dependencies. The escript is the honest untrusted
  entrypoint.
- **Timeout safety.** A timeout polls for the pgid file and, if the wrapper never
  recorded one, removes the session rather than leaving an unobservable process.
  A deliberately `setsid`-escaped process is documented as a residual M1.5-04
  concern.

### Part 3 — adversarial review hardening

- **Runtime client environment.** Step values are written to a 0600 file inside a
  private per-session 0700 host directory, copied into the container with
  `docker cp`, and loaded by the wrapper before the step. `--env-file`/client-env forwarding was rejected
  because a pipeline could set `DOCKER_HOST`, `HOME`, `LD_PRELOAD`, etc. and
  change the runtime client itself. Multiline values are escaped and decoded
  with `printf '%b'`.
- **Symlink-aware paths.** `TinyCI.Execution.Paths` resolves existing
  components (including intermediate symlinks) before comparing with the
  resolved project root. Preflight refuses symlinked working directories that
  escape, and untrusted runs skip artifact persistence entirely.
- **Secrets symlink.** Untrusted CLI runs pass `allow_symlink: false`, so a
  repository-controlled `.tiny_ci`/`secrets` symlink (final component or parent
  directory) is refused instead of read.
- **Rootless Podman.** Runtime probing records `rootless`, and the backend uses
  `--userns=keep-id` plus a `:Z` workspace/git label for Podman. A tagged
  `:podman` smoke test covers it.
- **Session tags.** Cleanup labels include a random nonce and both the run and
  session labels, so a failed open in one VM cannot remove another VM's
  containers.
- **Timeout fallback.** If the pgid file never appears, the whole stage session
  is removed (documented tradeoff). Missing-pgid tests cover it.
- **Tests.** Added symlink/paths tests, hostile runtime-env tests, `.git`
  read-only tests, failed/timed-out/hook cleanup tests, missing-image cleanup,
  and a Podman smoke test.
