# M1.5-04 — Run process tree and hard cancellation

**Milestone:** M1.5 · **Size:** M–L · **Depends on:** M0-06, M1.5-01 · **Status:** ⬜ Draft
**Written against:** commit `e9f5b8c` (2026-10-10)

## Summary

The ROADMAP's central bet is that the BEAM gives CI a run model other stacks have to assemble from
Redis, a queue, and a worker fleet: *"a run in flight → one supervised process tree"* and
*"cancel/timeout/crash isolation → kill the process tree"* (`ROADMAP.md:21-27`). That bet is not
yet true in the code. `TinyCI.Application` (`lib/tiny_ci/application.ex`) supervises only a
`Task.Supervisor` and a `Control.Registry`; a run is a loose set of unlinked tasks with no owner, no
address, and no hard cancellation.

This task makes the bet real **in core**, so the CLI and any future server start the *same*
supervised run:

- a `TinyCI.Run` GenServer per run under a `DynamicSupervisor` (`TinyCI.RunSupervisor`);
- a `TinyCI.OSProcesses` registry of every OS pid a run spawns, so a run can be killed completely;
- a `TinyCI.Runner.run_spec/2` facade (executor + hooks) used by both entrypoints;
- hard cancellation: `TinyCI.Run.cancel/1` kills the OS subtree **and** the executor task.

This is the core of what `M2-01` currently specifies. Moving it into core here means M2-01 becomes
wiring (`TinyCI.Server.Runs` → core `RunSupervisor` + an `EventBus` sink) rather than a second
process model.

## Why now

- Invariant **I2** (`M1.5-00`): no clean cancellation and no per-run home blocks the scheduler
  (M1.5-05) and the server (M2-03).
- The CLI gets a real cancellation primitive too (e.g. a breakpoint's abort can become a hard
  cancel), which is a local win, not only a server one. Note that no CLI cancel *trigger* exists
  today: there is no `--cancel` flag, and Ctrl-C is not simply wired up — `:os.set_signal/2` cannot
  handle SIGINT, so the BEAM break handler (and the Burrito wrapper, M1-03) decide what Ctrl-C
  does. Wiring Ctrl-C to `TinyCI.Run.cancel/1` needs its own design and is out of scope here.
- Doing it in core once prevents the CLI and server from diverging — the exact thing M1.5-01 exists
  to prevent.

## In scope

Core (`tiny_ci`):

1. `TinyCI.OSProcesses` — a named public ETS table (`:tiny_ci_os_processes`, `:bag`) of
   `{run_id, os_pid}`; `register/2`, `unregister/2`, `list/1`, `kill_all/1`. Created in
   `TinyCI.Application.start/2`. `TinyCI.Output` (Local backend) registers/unregisters when a
   `run_id` is present.
1a. **Open sessions per run.** `TinyCI.Execution.with_session/2` (M1.5-01) registers each open
   session as `{run_id, backend, session}` (a second table, or a tagged entry in the same one) and
   unregisters it in `close/1`. Cancellation calls `backend.close/1` on every open session. For
   Local this is a no-op; for Container (M1.5-02, D3) it is `docker rm -f`, which is the only way
   to stop processes inside the container — killing the `docker exec` clients does not.
2. `TinyCI.Runner.run_spec/2` — the single executor+hooks entrypoint, extracted from `CLI.Run`.
3. `TinyCI.Run` GenServer — generates the run id, builds the context, runs
   `Task.Supervisor.async_nolink(...)` inside the guarded executor, tracks status
   (`:starting | :running | :passed | :failed | :aborted | :cancelled | :crashed`), and owns
   cancellation. Broadcasts status transitions via an injected sink or the existing
   `Events` stream.
4. `TinyCI.RunSupervisor` — a `DynamicSupervisor` with `restart: :temporary` children; `start_run/1`,
   `cancel/2`, `status/1`, `list_active/0`.
5. `TinyCI.Runs.mark/3` — finalise `meta.json` for runs that never emitted `run_finished`
   (cancelled/crashed); add `:cancelled`, `:crashed`, `:interrupted` statuses.
6. `project_id` override honoured by `TinyCI.Artifacts` and `TinyCI.Runs` (server runs live in
   per-run workspaces so id cannot be derived from `root`).
7. `TinyCI.CLI.Run` starts its run through `TinyCI.RunSupervisor` instead of calling the executor
   inline. Behaviour and console output unchanged.

## Out of scope

- HTTP, queueing, git checkout, forge integration (M2).
- Restarting in-flight runs after a node restart — a run interrupted by a restart is `:interrupted`
  in history.
- Distributed cancellation across nodes (M4).
- Cooperative in-BEAM abort semantics beyond killing the process tree (unchanged).
- A user-facing CLI cancel trigger (a `--cancel` flag, or Ctrl-C / SIGINT handling); see *Why now*.

## Design notes

- `TinyCI.Run` must `trap_exit` and distinguish the executor task's normal reply from a `:DOWN`
  crash, so a crash becomes `:crashed` (recorded), never a lost run. See M2-01's pitfalls.
- Cancellation order: `Process.exit(task_pid, :kill)` first, so no new step or session can start;
  then snapshot `OSProcesses.list/1` and `kill_subtree/1` each; then `close/1` every open session;
  then `Runs.mark(:cancelled)`, then stop. Killing the BEAM task does **not** kill Ports' OS
  processes or containers — that is the whole reason `OSProcesses` and the session registry exist.
- The `Events.Dispatcher` is started inside the (killed) task, so its `close/1` may never run — hence
  `Runs.mark/3` writes the terminal status independently.
- Keep `TinyCI.Application` startable in tests with no config; the `DynamicSupervisor` and ETS table
  are cheap.

## Acceptance criteria

- [ ] `TinyCI.Runner.run_spec/2` is the single executor+hooks entrypoint, used by CLI and (later) server.
- [ ] A run is one GenServer under `RunSupervisor`, discoverable by id, exiting normally when done.
- [ ] `cancel/2` leaves no OS process of the run alive and records `cancelled` in history.
- [ ] An executor task crash is recorded as `crashed`, never lost.
- [ ] `project_id` override works end to end (run store and artifacts).
- [ ] `TinyCI.Application` starts the tree; tests need no config.

## Pitfalls

- `async_nolink` sends the reply **and** a `:DOWN`; `Process.demonitor(ref, [:flush])` after the reply.
- ETS `:bag` can hold duplicate `{run_id, pid}` if a pid is reused; use `:ets.delete_object/2` in
  `unregister/2`.
- Do not link the executor task to `TinyCI.Run`; the whole point is that the Run survives to record
  the failure.
- Never hard-code `docker` here: cancellation only calls `backend.close/1` on the registered
  sessions (item 1a), and the backend decides what closing means.
