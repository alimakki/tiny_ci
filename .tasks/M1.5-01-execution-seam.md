# M1.5-01 — Execution seam: one core, local and hosted

**Milestone:** M1.5 · **Size:** M · **Depends on:** M1-02, M1.5-07 · **Status:** ✅ Done
**Written against:** commit `e9f5b8c` (2026-10-10)

## Summary

Today a shell step's fate is hard-wired to the host: `TinyCI.Executor` calls
`TinyCI.Output.run_cmd/2`, which opens a `Port` on `sh -c <cmd>`. There is no seam for a server to
say "run this in the job's container," and no single place that expresses *where a step runs*.

This task introduces that seam: a `TinyCI.Execution.Backend` behaviour and a `TinyCI.Execution`
facade that every process-spawning call site goes through. The default is a **Local backend**
wrapping `TinyCI.Output` as M1.5-07 leaves it (collecting lines, printing nothing), so nothing
changes for existing local runs.

The point is not abstraction for its own sake. It is invariant **I1** from
[M1.5-00](M1.5-00-execution-fundamentals.md): mode (`:local` vs `:server`) selects *defaults and
policy*, never a different execution code path. After this task, `TinyCI.Executor` has no idea
whether it is running on a laptop or a server, and no `if server?` branches ever need to appear.

The contract follows decision **D4**: a backend spawns processes and reports output lines; it never
renders. It is session-shaped so the container backend (M1.5-02, decision **D3**) fits without
changing callers.

## Why now

Every later milestone needs this seam and it is cheapest to add while there are no users:

- M1.5-02 adds a **container backend** — it must slot in here.
- M1.5-03's `image:` needs a backend that can honour it.
- M2's server must run the *same* `TinyCI.Executor`; without the seam it would either fork the
  executor or shell out differently, which is exactly the local/CI drift we are trying to avoid.

## In scope

1. `TinyCI.Execution.Backend` — the behaviour (see Design): `name/0`, `available?/0`, `open/1`,
   `exec/3`, `close/1`.
2. `TinyCI.Execution.Command` and `TinyCI.Execution.SessionSpec` — small structs for what to run
   and where (see Design).
3. `TinyCI.Execution.Backend.Local` — `open/1` and `close/1` do nothing; `exec/3` wraps
   `TinyCI.Output`. It registers the OS pid with `TinyCI.OSProcesses` when a `run_id` is present
   (that module lands in M1.5-04; until then a guarded no-op, or this task brings the registry
   forward).
4. `TinyCI.Execution` — the facade: `with_session(spec, fun)` (opens, yields, closes in `after`) and
   `exec(session, command, on_line)`. Backend selection is **not** here yet: this task always
   selects Local unless an explicit `backend:` is given. M1.5-02 adds `TinyCI.Execution.Policy`
   (decision D1) and plugs it in at the one place a backend is chosen.
5. `ctx.trust` — added to the run context with the mode default (`:local` → `:trusted`,
   `:server` → `:untrusted`; D1), read from `Application.get_env(:tiny_ci, :mode, :local)`. Nothing
   acts on it in this task beyond the explicit error below; M1.5-02 adds the policy.
6. Wire every process-spawning call site to `TinyCI.Execution` instead of `TinyCI.Output`. As of
   `e9f5b8c` these are:
   - `Output.run_cmd/2` — `TinyCI.Executor` (`executor.ex:1342,1348`, `run_cmd_with_timeout/3`) and
     `TinyCI.Hooks` (`hooks.ex:80`);
   - `Output.run_executable/3` — only the sandbox backends, `TinyCI.Sandbox.Backend.Bubblewrap`
     (`bubblewrap.ex:46`) and `TinyCI.Sandbox.Backend.Seatbelt` (`seatbelt.ex:48`).
     `TinyCI.Executor.Driver.Sandbox` does not call `Output` itself. These are host-side
     confinement wrappers that only run in trusted runs (D2), so they call
     `TinyCI.Execution.Backend.Local` directly with an argv `Command`, bypassing policy.
7. The executor opens a session per stage (and per matrix combination) and passes it to each step;
   hooks open one session. With Local this costs nothing; it is the shape D3 needs.

## Out of scope

- The container backend, `TinyCI.Execution.Policy`, and `--isolate` (M1.5-02); `image:` (M1.5-03).
- Workspace location and per-run checkout (M2-02) — this task is only *process execution*.
- Changing output format, redaction, or the event stream (M1.5-07 already moved rendering to sinks).
- Any new dependency.

## Design

```elixir
defmodule TinyCI.Execution.Command do
  @enforce_keys [:run]
  defstruct [:run, env: %{}, working_dir: nil, timeout: nil]
  # run: {:shell, String.t()} | {:argv, executable :: String.t(), [String.t()]}
end

defmodule TinyCI.Execution.SessionSpec do
  @enforce_keys [:workspace]
  defstruct [:workspace, :run_id, image: nil, network: true, limits: %{}]
  # image/network/limits are ignored by Local and consumed by Container (M1.5-02/03).
end

defmodule TinyCI.Execution.Backend do
  @type session :: term()
  @type outcome :: {:passed | :failed | :timeout, output :: String.t()}

  @callback name() :: atom()
  @callback available?() :: boolean()
  @callback open(TinyCI.Execution.SessionSpec.t()) :: {:ok, session} | {:error, term()}
  @callback exec(session, TinyCI.Execution.Command.t(), on_line :: (String.t() -> any())) ::
              outcome
  @callback close(session) :: :ok
end
```

- **`on_line` is the only output channel.** The executor passes a callback that emits a
  `StepOutputLine` event; the console sink renders it (M1.5-07). A backend never prints, prefixes,
  buffers for display, or redacts — redaction stays at the dispatcher, and the executor still masks
  the returned `output` for `StepResult`.
- **`exec/3` owns the timeout.** On `:timeout` the backend has already killed the step's whole
  process tree (Local: `kill_subtree/1` as today; Container: the in-container process group, D3).
- **`close/1` is idempotent** and is always called from an `after` path, so a crashed or cancelled
  stage cannot leak a session.
- The executor resolves the backend once per run and stores it on the context; it opens sessions at
  stage/matrix-combination boundaries and passes them down. No per-step config lookups and no
  backend threaded through unrelated function signatures.

**Mode is policy, not plumbing.** A run in `:server` mode marked `:trusted` and a run in `:local`
mode both use Local and must produce identical results. Add a test that asserts precisely that: if
it ever fails, someone has added a mode branch to the executor.

## Pitfalls

- Sessions are the shape D3 needs, but resist designing the container lifecycle here — Local's
  `open`/`close` should stay trivial, and the contract should only promise what both backends can
  keep.
- Do not introduce a behaviour with a *single* implementation and then never add the second — if
  M1.5-02 slips, this task still stands on its own (it is the seam), but note it in Follow-ups.
- Matrix combinations run concurrently; each needs its own session even though Local makes that
  invisible. The fake-backend test (TDD 4) is what catches a shared session.

## Deviations

- `with_session/3` takes the backend as a `backend:` option; the task draft said `with_session/2`.
  The executor resolves the backend once and passes it explicitly.
- `run_pipeline/3` and `execute/4` accept a programmatic `:backend` option. It is the injection
  point for tests and for the future policy; it is not a CLI flag.
- `ctx.trust` is a dynamic context key (like `:run_id`), not a `TinyCI.Context` struct field. The
  executor fills it from `Application.get_env(:tiny_ci, :mode, :local)` when the caller did not set
  one.
- An untrusted run with no backend fails at the run level: `run_pipeline/3` emits
  `pipeline_started` + a failed `pipeline_completed` and returns
  `{:error, {:execution_unavailable, reason}, []}`; standalone `execute/4` raises
  `TinyCI.Execution.Error`. No stage starts.
- `TinyCI.OSProcesses` registration is deferred to M1.5-04. Local's session ref carries `:run_id`
  so that task can register pids without changing the contract.
- The sandbox backends' `sandbox_exit` error no longer carries a numeric exit code: the backend
  contract reports status plus output. It now reports `{:sandbox_exit, :failed, output}`. No test
  asserted the code.
- Hooks open one Local session per shell hook. M1.5-02 may group the hook phase into one session to
  match D3's "hook session"; the contract does not change either way. A shell hook in an untrusted
  context fails closed: `Execution.backend/2` raises, `safe_run_hook/2` records the hook failure,
  and no host process starts.
- A regular stage's session spans its body, its `after:` boundary, and any stage retry. Matrix
  stages open one session per combination per attempt.
- `Execution.backend/2` re-validates a stored backend instead of trusting it, so a pre-set Local
  backend cannot smuggle an untrusted run onto the host.
- The I1 parity tests live in `test/tiny_ci/execution_parity_test.exs` (`async: false`, because they
  set `Application.put_env(:tiny_ci, :mode, ...)`) and actually run under both `:local` and
  `:server` mode. Session integration tests live in `test/tiny_ci/executor_execution_test.exs`
  (async) rather than appended to the 2,500-line `executor_test.exs`.
- Sandbox launchers receive the run id through `Driver.Sandbox`'s backend options, so their Local
  session can be registered by M1.5-04.
- `TinyCI.Output` keeps its public `redact:` option and its tests; the execution backend never
  passes it. Masking stays in the dispatcher for events and in `StepResult`/hooks for returned
  output.
