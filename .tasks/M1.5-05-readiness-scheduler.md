# M1.5-05 — Readiness-based DAG scheduling and a global concurrency cap

**Milestone:** M1.5 · **Size:** M · **Depends on:** M1.5-04 · **Status:** ⬜ Draft
**Written against:** commit `e9f5b8c` (2026-10-10)

## Summary

Two scheduling defects will bite the moment a run is more than a toy:

1. **Level barriers.** `TinyCI.DAG.build_levels/1` (Kahn BFS) groups stages into levels, and
   `execute_dag_levels/4` (`executor.ex:325-350`) waits for *every* stage in a level before starting
   the next. So in `A → {B, C} → D`, if `B` is slow and `C` is fast, `D` still waits for `B`. The
   graph knows `D` could start as soon as `B` is done; the scheduler does not. `docs/reliability.md`
   calls this out (`:43-45`).
2. **No global cap.** Nothing bounds the total number of concurrent OS steps. A wide matrix or many
   parallel stages can fork hundreds of processes at once. There is no `--concurrency`, no per-run
   ceiling.

This task replaces level-barrier execution with **readiness-based** scheduling and adds a **global
concurrency cap**. `DAG.validate/1` (cycle/unknown detection) stays; `build_levels/1` is retired from
the execution path.

## Why now

- Invariant **I2** and the scheduler M2-03 expects to build on. A server with a FIFO queue is only as
  good as the scheduler underneath it.
- It directly changes wall-clock time for real pipelines (the ROADMAP's M5 "speed" milestone assumes
  it).
- The cap is also a safety property: it bounds the blast radius of a pathological pipeline before the
  server exists to enforce per-repo limits.

## In scope

1. `TinyCI.Scheduler` — given stages, their `needs`, and a completion callback, start a stage as soon
   as all its dependencies are satisfied; propagate `:skipped`/`:blocked` promptly; preserve the
   existing sequential semantics when no stage has `needs:` (the current `dag_mode?/1` distinction
   stays).
2. Rewire `TinyCI.Executor`'s DAG path to use `TinyCI.Scheduler`; delete `build_levels/1` and
   `execute_dag_levels/4` from the execution path (keep `DAG.validate/1`). Keep `DAG.dag_mode?/1`.
3. **Global concurrency cap** — a `--concurrency N` flag (default: `System.schedulers_online() * k`
   or a fixed default; decide in Design), plus `config :tiny_ci, :max_concurrency`. Enforced by a
   counting semaphore shared by parallel steps, DAG stages, and matrix combinations (one ceiling for
   the whole run, not per stage). This is the BEAM-side cap; M1.5-02's cgroup limits are the
   OS-side floor.
4. Store-merge semantics under readiness scheduling: a stage sees the stores of its completed
   `needs:` (currently "explicit writes merged in declaration order", `docs/reliability.md:14-15`);
   preserve that contract and test it, because the barrier is what made it easy before.
5. Deterministic event ordering is preserved: the `Events.Dispatcher` already serialises emission, so
   concurrency must not reorder `StageStarted`/`StageCompleted` pairs within a stage.

## Out of scope

- Priority scheduling, fairness, or a persistent queue (M2-03).
- Distributed scheduling across nodes (M4).
- Changing `needs:` semantics or adding new DAG directives.
- Retry/backoff policy changes.

## Design notes

- Model the scheduler as a small pure core (`ready?/2`, `advance/3`) plus a thin process layer that
  spawns ready stages on `TinyCI.TaskSupervisor` and awaits completions with `Task.yield_many`.
  Prefer a receive-based loop driven by task completion messages over polling.
- The semaphore can be a `:counters`-backed gate or a `GenServer` with grants; it must be created
  once per run (not global) so runs do not starve each other, and released in `after` paths on
  timeout/cancel/crash. Ties to M1.5-04's cancellation (release on kill).
- Keep the "sequential when no `needs:`" path byte-identical to today; readiness scheduling is the
  DAG path only.
- Default cap: prefer a real default that no one hits (e.g. `2 × schedulers`) over "unbounded," so the
  pathological case is bounded out of the box.

## TDD plan (to be finalized)

1. `test/tiny_ci/scheduler_test.exs` (pure core): a diamond starts D on B's completion without
   waiting for C (dummy callbacks, no real work); `:skipped`/`:blocked` propagate; unknown dep is an
   error; no-`needs` is rejected by the DAG path and handled sequentially.
2. `test/tiny_ci/executor_test.exs` — "readiness scheduling": stages `slow` (sleeps, marked via a
   file/marker), `fast`, and `after_slow` (`needs: [:slow]`); assert `after_slow` starts before
   `slow`'s siblings in the same old level would have finished — better: assert via event timestamps
   that `StageStarted(after_slow)` precedes `StageCompleted(fast)` when `fast` outlasts `slow`.
   Deterministic version: make `fast` sleep longer than `slow` and assert ordering.
3. `test/tiny_ci/executor_test.exs` — "global cap": 8 parallel steps with `max_concurrency: 2` never
   run more than 2 OS processes at once (each step records start/stop timestamps in a temp file;
   assert the max overlap ≤ 2).
4. Store-merge regression: a stage with two `needs:` sees both stores; declaration-order precedence
   holds.
5. Full suite; `mix tiny_ci.run`.

## Acceptance criteria

- [ ] A dependent stage starts the moment its `needs:` complete, ignoring unrelated siblings.
- [ ] `DAG.validate/1` still catches cycles and unknown stages; `build_levels/1` is gone from the
      execution path.
- [ ] A run-level concurrency cap is enforced across stages, steps, and matrix combinations, and is
      configurable via flag + config.
- [ ] Sequential semantics for `needs`-free pipelines are unchanged (guarded by existing tests).
- [ ] Store-merge contract (`docs/reliability.md:14-15`) is preserved and tested.
- [ ] `docs/reliability.md` "DAG execution has level barriers" boundary is removed.

## Pitfalls

- Several existing DAG tests assert level-barrier timing; rewriting them is expected and must be
  called out per CONVENTIONS, not silently relaxed.
- Semaphore grants must be released on every exit path (timeout, cancel, crash) or a run deadlocks
  after a failure.
- Do not serialise the whole run to make ordering easy; ordering is the dispatcher's job, not the
  scheduler's.
